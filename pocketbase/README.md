# KsuNiMeet на PocketBase

Бэкенд для сайта: **фронтенд — статика на GitHub Pages, сервер — PocketBase**.
Один Go-бинарник, внутри SQLite, REST, права доступа, файлы и живые обновления.

Это замена Supabase. Приложение (`app.js`, `watch.js`, `call.js`) **не
переписано**: к нему подключён адаптер `public/pb.js`, который повторяет
интерфейс `supabase-js` поверх PocketBase. Причина — в этих файлах уже сидит
отдельно отлаженная работа с российским каналом (дедлайны, повторы, зеркала,
оптимистичная отправка), и переписывать её под другой бэкенд значило бы заново
ломать то, что работает.

## Что где лежит

| путь | что это |
|---|---|
| `pb_migrations/1750000000_ksu_init.js` | схема: коллекции, индексы, правила доступа |
| `pb_migrations/1750000100_films_idx_optional.js` | правка схемы после первого выпуска |
| `pb_hooks/ksu.pb.js` | регистрация хуков (что и когда делать) |
| `pb_hooks/ksu_lib.js` | код хуков: номер, `chat_key`, `seq`, уборка |
| `run-local.ps1` | запуск на Windows: скачать, поднять, автозапуск |
| `../vps/pocketbase-install.sh` | установка на сервер (systemd + Apache) |
| `../vps/pocketbase-proxy.conf` | проксирование `/pb/` в Apache |

Клиентская часть: `../public/pb.js` (адаптер), `../public/backend.js` (выбор
клиента по `backend` в конфиге), `../public/config.example.js` (образец).

## Быстрый старт локально (Windows)

```powershell
powershell -ExecutionPolicy Bypass -File ksunimeet-web\pocketbase\run-local.ps1
```

Первый запуск сам скачает бинарник и накатит схему. Панель администратора —
`http://127.0.0.1:8090/_/`, первый суперпользователь:

```powershell
& ksunimeet-web\pocketbase\pocketbase.exe superuser upsert ВАШ@email ПАРОЛЬ --dir ksunimeet-web\pocketbase\pb_data
```

Затем рядом поднимается сам сайт и в конфиге указывается адрес сервера:

```bash
node ksunimeet-web/tools/serve.mjs 8137     # http://127.0.0.1:8137
```

```js
// ksunimeet-web/public/config.js
window.KSU_CONFIG = { backend: 'pocketbase', pbUrl: 'http://127.0.0.1:8090' };
```

Адрес из `pbUrl` обязан быть в списке `--origins` у PocketBase, иначе браузер
отобьёт ответы как чужие (CORS). У `run-local.ps1` список уже включает порт
разработки; у сайта на GitHub Pages в нём должен стоять адрес сайта.

## Установка на сервер (рекомендуется)

```bash
bash vps/pocketbase-install.sh --dry-run    # посмотреть, что будет
bash vps/pocketbase-install.sh              # сделать
```

Скрипт кладёт код, ставит systemd-юнит (перезапуск при падении), настраивает
прокси `/pb/` в Apache и сам проверяет три вещи: API на петле, API через Apache,
поток живых обновлений. `pb_data` при повторном запуске не трогается.

После установки — переменные в GitHub (Settings → Secrets and variables →
Actions → **Variables**):

| переменная | значение |
|---|---|
| `KSU_BACKEND` | `pocketbase` |
| `POCKETBASE_URL` | `https://ksunimeet.b4rn1.com/pb` |

Следующая публикация соберёт из них `config.js` (см.
`../.github/workflows/pages.yml`). Панель администратора наружу не открыта —
к ней ходят туннелем:

```bash
ssh -L 8091:127.0.0.1:8090 root@45.32.156.137   # затем http://127.0.0.1:8091/_/
```

## Почему сервер, а не домашняя машина

Машина может работать круглосуточно, но этого мало: домашний сервер нужно ещё
сделать доступным снаружи. И тут важна именно российская сторона вопроса.

| способ | годится для России? |
|---|---|
| **VPS напрямую** (этот путь) | **да.** Уже отвечает из России, уже переведён на HTTP/1.1, TLS напрямую, без CDN |
| Cloudflare Tunnel | **нет.** Трафик уходит в сеть Cloudflare, а её российские провайдеры режут с июня 2025 — заработало бы «у всех, кроме России» |
| ngrok, прочие туннели | **нет**, по той же причине: свой посредник на пути |
| проброс порта + домен + Let's Encrypt | технически да, но упрется в CGNAT у провайдера, будет ломаться при смене IP и требует, чтобы машина не спала |

Тот же самый бинарник работает и на домашней машине (`run-local.ps1`), и это
удобно для проверки. Но **боевым адресом для России должна быть машина,
доступная напрямую** — та, где сайт уже живёт.

Отдельно про «в России приоритет»: приоритет держится не на бэкенде, а на
`net.js` — у каждого запроса есть дедлайн и повтор, есть зеркала, и список
адресов проверяется пробой. Бэкенд лишь обязан быть тем, что **не рвётся на
16 килобайтах**: поэтому PocketBase отдаёт события как обычный длинный
HTTP-ответ (SSE), а Apache не сжимает и не буферизует этот поток
(`vps/pocketbase-proxy.conf` — это самое хрупкое место связки).

## Что такое `bus` и `presence`

У PocketBase нет ни broadcast-каналов, ни presence, как у Supabase Realtime:
он умеет только «строка изменилась». Поэтому:

- **`bus`** — «пинг»: запись «кому», «от кого», «какого рода событие». Это
  будильник, а не данные: в нём **нет тел сообщений**. Получатель, проснувшись,
  идёт за текстом в `messages`, где правилом доступа решает база. Подделанный
  или чужой пинг поэтому ничего не показывает и не может поднять фальшивый
  звонок. По этой же коллекции летит сигналинг WebRTC (SDP и ICE), пульт
  фильма и «кто здесь».
- **`presence`** — сердцебиение: клиент переписывает время каждые 10 секунд,
  уборщик удаляет записи старше 45. Следствие, о котором стоит знать: выход
  из комнаты виден не мгновенно, а в пределах одного тика. У Supabase это было
  мгновенно, потому что отключение замечал сам сокет.

## Схема

| коллекция | замена | правила (кто что может) |
|---|---|---|
| `profiles` | `auth.users` + `profiles` | вход по имени; поиск — вошедшим; правка — только своя |
| `contacts` | `contacts` | вижу и правлю только свои |
| `messages` | `messages` | свои переписки; писать только от своего имени; «прочитано» — только получатель |
| `calls` | `calls` | только звонки со своим участием; состояние меняет любой из двоих |
| `rooms` | `rooms` | чтение — вошедшим по коду; правка — только хозяин |
| `bus` | `room_events` + broadcast | чтение/запись — вошедшим |
| `presence` | `room_peers` (+ presence) | вошедшим |
| `films` | bucket `ksu-films` | по коду комнаты; части режутся так же по 45 МБ |

Почты нет вовсе: `email` необязателен, вход идёт по `username`
(`passwordAuth.identityFields`). Минимум пароля снижен с 8 до 6 — ровно то, что
обещает экран входа.

### Что сервер делает сам (хуки)

Клиент этого делать не должен и не может:

- **номер** (`phone`, 8 цифр) выдаёт сервер — иначе любой занял бы чужой;
- **`chat_key`** собирается из двух id по возрастанию: у пары ровно один канал;
- **`seq`** — монотонный номер сообщения. У PocketBase id случайная строка, а
  приложение ждёт от `messages.id` числа, растущего со временем. Адаптер отдаёт
  `id = seq`, и «сортировка по времени» и «что новее maxId» снова работают;
- **уборка** раз в минуту: присутствие старше 45 с, пинги старше 10 мин,
  неотвеченный звонок → `missed` через 27 с, комнаты старше 12 ч, части фильмов
  без живой комнаты.

## Что проверено на живом сервере

Не «должно работать», а проверено запуском (PocketBase 0.40.5, Windows-сборка,
реальный браузер):

- регистрация без почты и **без номера** — номер выдаётся сервером, у двух
  аккаунтов разный; пароль из 6 символов принят; дубликат имени отвергнут;
- вход по имени; чужой `sender_id` при отправке отвергается правилом; аноним не
  видит ни одного сообщения;
- `chat_key` и `seq` выдаются сервером, `seq` растёт, оба направления дают один
  и тот же `chat_key`;
- **живая доставка**: сообщение, отправленное в одной вкладке, появилось во
  второй (в фоновой!) без перезагрузки — то есть `bus` + SSE + выбор канала по
  `topic` работают;
- поиск человека по имени (перевод фильтра `or`/`ilike`) находит по имени;
- **фильм**: часть заливается, скачивается байт в байт, повторная заливка
  перезаписывает, а не создаёт дубль, отсутствующая часть даёт понятную ошибку;
- **присутствие**: `presenceState()` отдаёт `{ключ: [{role, name}]}` — ровно ту
  форму, которую читает `watch.js`; выход снимает подпись;
- **уборщик не сносит фильм живой комнаты** (иначе кино пропадало бы через
  минуту) и убирает сироту — проверено ожиданием полного прохода.

## Известные ограничения

- **Фоновый опрос в APK.** Нативная часть (`apk converted/`) обращается к
  Supabase REST напрямую, своим сохранённым токеном. С PocketBase этот путь
  сломан: токен и адреса другие. Веб-часть работает полностью, но уведомления
  в свёрнутом приложении требуют отдельной правки — заменить в `NotifService`
  адрес и заголовки на PocketBase (`/api/collections/messages/records?filter=…`,
  `Authorization: <token>`). Это единственный известный незакрытый разрыв.
- **`bus` виден всем вошедшим.** В нём нет тел сообщений, но метаданные
  («кому», «от кого») видны. Для 30–50 человек это приемлемо; если станет
  важно — вынести по адресату в отдельные коллекции.
- **Присутствие не мгновенно**, см. выше: до одного тика (≈45 с на выход).
- **Уборка зависит от clock**: сравнение дат идёт строками в формате PocketBase,
  одинаковыми и в UTC.
- **Панель администратора не публична** — только через SSH-туннель (сделано
  нарочно).
- Схема проверялась на **PocketBase 0.40.5**; до версии 1.0 автор проекта не
  обещает совместимости, поэтому при обновлении читайте их changelog.
- В коде приложения остался англоязычный `email`-подобный вход, который адаптер
  превращает в имя (часть до `@`). Это сделано, чтобы не трогать рабочие файлы.
